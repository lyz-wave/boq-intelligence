01 · Problem & Core Breakthrough

为什么传统文本 AI 会搞砸造价匹配？

项目围绕「工程造价数据资产化 + 语义标准化 + 智能匹配出估算表」双轨目标展开。真实造价数据中，字面高度相似但核心规格不同的条目，综合单价可相差近 10 倍。

行业痛点 01 · 数据孤岛

多专业提资格式极度异构

水利概算导表（万元口径）、土地整治（14列合并空列 + 2564行斜杠拼接单价分析表）、国标安装 PDF（跨页断词）混杂，技经人员 30%+ 时间消耗在手工整理核对。

行业痛点 02 · 效率与偏差

人工套价慢且人为差异大

传统收资套定额需 3~5 个工作日，不同编制人对定额与信息价理解不同导致同类成果偏差达 8%~10%。业务刚需：按省/工程类型建库，搜最相似项一键出估算表。

核心破局 · 双库 + 混合核

三层四维标准 + 硬规格衰减核

先将非标文件清洗为 L0/L1/L2 三级结构化资产，再通过“多路召回 + 硬规格指数衰减核 + L2 工料机调差”，实现精准匹配、可解释溯源与一键导出原生公式 Excel。

04 · Matching Algorithm & Live Sandbox

智能价格匹配算法：多路召回 + 硬规格衰减核 + 工料机重算

在右侧和下方可以直接拖动滑块，现场演示“硬规格衰减核如何防错配”以及“主材涨价如何联动 L2 定额重算单价”。

STAGE 1 · 多路召回 + RRF
S_RRF(d) = Σ 1 / (60 + rank_r(d))

BM25 工程分词（精确命中型号/定额号）+ Char N-gram SVD 向量（召回清表/地表清理同义词）+ Slot 结构化匹配，再经物理量纲族过滤。

STAGE 2 · 硬规格指数衰减核
Φ(x_q, x_c) = exp(-α · |x_q - x_c| / max)

先通过正则计算标量（如 3×150+1×95 = 545 mm²），相对偏差 > 30% 时触发硬冲突熔断（总分封顶 0.58，标记红灯预警）。

STAGE 3 · 多维融合与 SHAP 归因
S = 0.65·S_feat + 0.22·S_sem + 0.13·S_ctx

按 YAML 配置的 AHP 权重聚合槽位分，叠加同省份/同阶段/时间亲和分，输出 🟢/🟡/🔴 置信度与 SHAP 维度贡献条形图。

05 · References & Innovations

我们借鉴了哪些开源项目与理论？又做了哪些工业超越？

站在工程造价开源社区与前沿信息检索、可解释 AI 研究之上，结合国内水利与土地整治多定额真实场景做了深度重构。

1. BruceLee1024/cost-data（及 zaojia-database） 造价数据结构借鉴

借鉴点：学习其“项目库—清单库—定额分析库—材价库”四库联动本地优先工作台思路，解决造价表与单价分析表分离问题。

我们的超越：设计L0/L1/L2 三级渐进存储模型，同时兼容缺 L2 的水利概算单行本与带 2564 行定额分析表的土地整治预算；引入 YAML 领域本体覆盖 7 大工程专业。

2. KanadeK/boq-check（原 boq-lint） 合规检查规则借鉴

借鉴点：学习其将造价审查拆分为独立规则编号（BQ001~BQ016）、过滤章节小计行、归一化单位写法（m2/㎡/m²）的 Linter 插件架构。

我们的超越：升级为结合历史价格均值偏离（BQ009 ±25%）、置信度红灯阻断（BQ010）与工作内容防重计价提示（BQ012 电缆终端头与电缆含头提示）的后端可插拔审查引擎。

3. Bidwright & DDC-CWICR（OpenConstructionEstimate） 流水线与契约借鉴

借鉴点：借鉴 Intake → Takeoff → Pricing → Quote 四阶解耦流水线与 Canonical Schema（先统一中间态再入向量库）工程范式。

我们的超越：针对国内《水总〔2024〕323号》《财综〔2021〕128号》《GB50500-2024》计价体系，补充 Word 编制说明上下文抽取与跨区域主材价差自动重算。

4. 混合检索、AHP/SHAP 可解释 AI 与 ES-CBR 算法与科研创新

借鉴点：借鉴 RRF 多路融合、层次分析法（AHP）专家权重矩阵、SHAP 边际特征归因以及案例推理指数平滑（ES-CBR）。

我们的超越：首创硬规格数值求值 + 指数衰减核函数消除“字面相似但规格差 9 倍”陷阱，并把 LSTM+Cosine 与 R-GCN 挂载为同平台消融实验插件，一套底座同时满足生产与科研论文交付。

06 · Architecture Decision Records (ADRs)

为什么这么设计？四大核心架构权衡（点击展开详情）

每一项架构选择都有明确的工程权衡，已沉淀为仓库中的 4 份正式 ADR 文档。

ADR-0001：为什么采用“微内核 + 六大深模块 + 插件注册表”，而不是传统 MVC 或微服务？ 架构可维护性
放弃方案：
• 传统三层 MVC：解析、正则、打分全缠在 Service 层，新增一种非标 Excel 都要动核心代码。
• 重量级微服务：内网或单机开箱部署运维成本过高。
最终方案收益：
• 单体进程内极简部署（SQLite + FastAPI 零依赖）。
• 新增造价表格式、匹配算法或 BQ 规则，只需在对应目录新增 1 个文件 + @PluginRegistry.register，核心零修改。
ADR-0002：为什么采用“YAML 领域本体 + 正则优先 / LLM 兜底”，而不是全量调大模型？ 速度与离线可用
放弃方案：
• 全量依赖 LLM / BiLSTM：几千条清单批处理耗时过长、算力开销大，且企业涉密造价数据往往要求纯内网离线运行。
最终方案收益：
• 85%+ 的工程规格（电缆截面、运距、地径、标号）由 Tier-1 YAML 正则在 <1ms 内 100% 确定性抽出。
• 新增第 8 个工程专业只需写 1 份 YAML，无需写一行 Python。
ADR-0003：立项书写的“LSTM + 余弦相似度 + 知识图谱”怎么落地与升级？ 科研与生产双赢
发现的工程缺陷：
• 实测证明纯文本余弦相似度无法区分 3×150+1×95（1194.67元）和 3×25+1×16（133.15元），直接上线会严重报错价。
最终方案收益：
• 线上生产主线采用 多路混合召回 + 硬规格指数衰减核 + AHP 权重保证 0% 硬规格错配。
• 同时将 LSTM+Cosine、R-GCN 保留为 RerankerPort 实验插件，一键跑出论文消融对比数据。
ADR-0004：为什么设计 L0 / L1 / L2 三级存储？缺乏定额分析表的概算项目能入库吗？ 颗粒度兼容
现实数据颗粒度差异：
• 概算单行本（如水利生态修复）只有 L1 综合单价 + Word 中的 L0 主材价；
• 施工图预算（如土地整治）额外带 86 块完整的 L2 定额工料机消耗分析表。
最终方案收益：
• L0 + L1 必选、L2 可选增强——两类项目均可 100% 入库。
• 调价时自动分级路由：有 L2 走主材价差精确重算，仅 L1 走地区/时间指数修正或直接复用。
